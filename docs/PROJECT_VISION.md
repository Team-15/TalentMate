# TalentMate 伴贤 · Project Vision

> 语音驱动的私人关系关怀助手
> 定位：帮你「记得」去联系家人、朋友和熟人，并把维护成本降到说一句话。

---

## 1. 我们要解决什么问题

私人关系的衰减同样是**静默发生**的。

一个人从「关系不错」滑到「很久没联系」，中间没有任何事件提示你 ——
没有报错、没有到期提醒、没有任何东西告诉你「你已经 117 天没和这个人说过话了」。
直到某天你需要他（要内推、要资源、要配合、要挽留），才发现关系已经凉了。

**问题不在于人们不在乎，而在于两件事同时成立：**

1. **看不见** —— 关系状态是隐性的，人脑不擅长追踪几十上百条关系的衰减曲线
2. **记不下来** —— 即使意识到了，把「和谁、什么时候、聊了什么、下次该什么时候跟进」
   记录下来这件事，**摩擦成本高到没人会坚持做**

第二点才是关键。所有关系管理工具最终都死于同一件事：**没人愿意录入数据。**
CRM 要求销售填表单，所以销售敷衍地填；人脉管理 App 要求手动记笔记，所以用三次就弃了。

**语音是唯一能把这个摩擦降到接近零的交互方式。**
刚见完一个朋友，走在路上，说一句「周末提醒我给妈妈打电话」——
3 秒，不用打字、不用找联系人、不用选日期。

### 为什么是现在

语音识别在过去两年才真正便宜且准确到可以支撑交互（腾讯云 ASR 的准确率已经足够）。
在此之前，这个产品在技术上不成立。

## 2. 目标用户

我们**不**面向所有人。明确聚焦在两类人：

### 主要用户：希望维系私人关系的个人

同时维护家人、朋友与熟人关系，容易「想联系却总忘记」的人。

**共同特征：**

- 关系质量**不被任何系统度量**，衰减悄无发生
- 同时维护十几到上百条私人关系，超出人脑可靠追踪的范围
- 已经在用日历和通讯录，但它们**互不相通** ——
  日历知道「周六有空」，但不知道「你已经 117 天没给妈妈打电话了」

**典型痛点场景：**

- 想起要联系某人时，已经过去大半年
- 节日到了才发现忘了给重要的人发问候
- 知道「应该多关心家人朋友」，但不知道**具体该先联系谁**

### 明确不服务的对象

- 追求销售漏斗管理的销售团队 —— 他们需要的是 CRM，不是关怀助手
- 只想存电话号码的人 —— 系统通讯录已经够了
- 想做社交的人 —— 这不是社交网络

## 3. 核心场景与痛点

### 场景 A：刚结束一场互动，需要记录并安排下一步

**现状：** 走出会议室，脑子里的信息（聊了什么、答应做什么、什么时候该跟进）
在接下来两小时内会被下一件事冲掉。想记下来，但要打开 App、新建日程、
填标题、选日期、选时间、选联系人、设提醒 —— 六七个动作，放弃了。

**我们要做的：** 一句话完成。
「周末提醒我给妈妈打电话」→ 识别意图、找到联系人、建日程、设提醒、生成问候邮件草稿。

### 场景 B：想维护关系，但不知道该找谁

**现状：** 「我应该多关心一下团队」是一个模糊的意愿，无法转化为具体行动。
打开通讯录，看到 80 个人名，然后关掉。

**我们要做的：** 主动告诉你「这 3 个人需要关注」，按紧急度排序，并给出原因
（「117 天未沟通」「长期未联系」）。把模糊意愿变成一份可执行的清单。

### 场景 C：批量建立关系档案

**现状：** 想把重要的家人朋友一次建进名册，手动一个个录入太慢。

**我们要做的：** 支持粘贴 CSV 批量导入，5 分钟建好名册。

### 场景 D：维护本身需要付出沟通成本

**现状：** 决定要联系某人后，还要想措辞、写邮件。

**我们要做的：** 基于联系人和日程自动生成关怀邮件草稿，用户只需要改几个字。

## 4. 产品愿景

> **让职业关系的维护成本低到不需要意志力。**

拆解成三条设计原则：

**① 零摩擦录入是产品的生命线**
所有功能都必须能被语音驱动。如果某个功能必须打字，它就不重要。
这不是「加个语音输入」，而是**以语音为主交互来重新设计信息架构** ——
这也是为什么必须做原生 App 而不是网页：麦克风权限、后台通知、系统级体验，
在浏览器里都做不到。

**② 主动提醒，而不是被动查询**
产品价值不体现在「用户想起来打开它」，而体现在**用户没想起来的时候它找你**。
所以本地通知是核心功能，不是附属功能。

**③ 只做「记得」，不做「替你决定」**
我们不试图变成 AI 秘书去替你社交。
产品做的是：让你**看见**该维护的关系、让你**记得**要做的跟进、帮你**省掉**起草的力气。
最终那句问候还是要你自己说 —— 这个边界要守住，
因为一旦 AI 替你说，关怀就变成了打扰，产品就变成了骚扰工具。

## 5. 项目范围

### 做（In Scope）

| 能力 | 为什么必须做 |
|---|---|
| 语音建日程 / 查询 / 取消 | 核心差异点，零摩擦录入的唯一实现方式 |
| 联系人名册（家人 / 朋友 / 熟人分组） | 关系维护需要对象，且私人关系有清晰圈层 |
| 关系状态判定（高优先级 / 需关注 / 正常） | 把「看不见」变成「看得见」，是产品的价值来源 |
| 关怀日程 + 日历视图 | 让安排有落脚点，且能回看历史 |
| 提醒与本地通知 | 「主动提醒」原则的落地，否则产品退化为被动工具 |
| 邮件草稿生成 | 降低「维护动作」本身的成本 |
| 关系洞察（统计与清单） | 场景 B 的入口，把模糊意愿变成行动清单 |
| CSV 批量导入 | 解决冷启动，否则新用户面对空名册会流失 |

### 明确不做（Out of Scope）

**刻意不做，而且要说清楚为什么：**

| 不做 | 原因 |
|---|---|
| 销售漏斗 / 商机 / 合同管理 | 那是 CRM 的领域，做了就变成「又一个 CRM」，失去聚焦 |
| 社交功能（动态、点赞、加好友） | 私人关系是私密的，公开化会摧毁使用意愿 |
| 团队协作 / 共享名册 | 涉及隐私与权限，复杂度极高，且不是核心痛点 |
| 完整邮件客户端 | 我们只解决「起草」，收发交给专业工具 |
| AI 自动发送消息 | 见愿景③，这是产品伦理边界 |
| 多端实时同步 | 工程量大，对核心场景（个人维护关系）收益低 |
| 第三方日历双向同步 | 有价值但非必需，且平台差异大，容易拖垮进度 |
| 数据分析 / 报表导出 | 面向个人的产品不需要 BI |

**判断标准：** 如果某个功能不能服务于「降低关系维护的摩擦」，就不做。
宁可窄而深，不要宽而浅。

## 6. 关键用户故事与流程

### 用户故事（按优先级）

**P0 — 产品的存在理由**

> 作为一个刚见完朋友的人，我想用一句话记录「周末提醒我给妈妈打电话」，
> 以便不用打开表单填六项内容。

> 作为一个团队 leader，我想知道**具体哪几个人**需要我关注，
> 以便把「应该多关心团队」变成今天就能做的三件事。

> 作为一个忙碌的人，我想在日程开始前收到提醒，
> 以便我真的去维护这段关系，而不是又一次错过。

**P1 — 支撑主流程**

> 作为新用户，我想粘贴 CSV 一次性导入团队名单，
> 以便不用一个个手动录入。

> 作为一个要联系某人的人，我想要一封已经写好的邮件草稿，
> 以便我只需要改几个字就能发出去。

> 作为用户，当我说的人名匹配到多个联系人时，我希望系统问我选哪一个，
> 以便不会把日程挂到错误的人身上。

**P2 — 完善体验**

> 作为用户，我想问「这周有什么安排」，以便快速回顾。

> 作为用户，我想说错时能取消或改期，以便不用手动去日程里删。

### 核心用户流程

**流程 1：语音建关怀日程（最关键路径）**

```
打开 App → 点击麦克风 → 说话
    ↓
语音识别（听到「周末提醒我给妈妈打电话」）
    ↓
意图解析（识别为「新建日程」，抽出：联系人=妈妈、时间=周末、事项=打电话）
    ↓
联系人匹配
    ├─ 唯一匹配 → 继续
    ├─ 多个匹配 → 询问用户选哪一个
    └─ 无匹配   → 退化为无关联日程（不报错）
    ↓
创建日程 + 设置提醒 + 生成邮件草稿
    ↓
展示结果：「已添加 1 个事件：给妈妈打电话，周六 10:00，已绑定妈妈」
```

**流程 2：主动关怀闭环（产品的长期价值路径）**

```
收到本地通知「10 分钟后：和张三的面试」
    ↓
点击通知 → 直达该日程
    ↓
完成后更新互动记录
    ↓
洞察页自动更新关系状态（该联系人从「需关注」移出）
    ↓
下一个需要关注的人浮现出来
```

这个闭环很关键：**它让产品有自我维持的动力**，
不需要用户「想起来用它」，而是它推动用户去完成维护动作。

**流程 3：冷启动**

```
注册 → 新手引导（说明价值）→ 空名册
    ↓
引导添加联系人 / 粘贴 CSV 导入
    ↓
名册建立 → 洞察页开始有意义 → 语音开始能绑定联系人
```

> 这里有个我们实测发现的产品细节：**名册为空时，语音只能创建无关联的日程**。
> 所以产品在名册为空时明确提示「建议先添加联系人」——
> 冷启动的引导质量直接决定用户能不能进入核心价值。

## 7. 为什么用户会选我们，而不是现有方案

### 现有替代方案的短板

| 方案 | 强在哪 | 弱在哪（我们的机会） |
|---|---|---|
| 手机通讯录 | 人人都有 | 只有静态信息，**不会提醒你维护关系** |
| 日历 App | 时间管理成熟 | 只知道「有什么会」，**不知道「和谁多久没联系」** |
| 微信 | 沟通在发生 | 是沟通工具，**不是关系管理工具**；不记录、不提醒 |
| CRM（Salesforce 等） | 管理能力强 | 重、贵、面向销售流程；**要求大量手工录入** |
| 人脉管理 App | 概念契合 | 手机上**录入体验差**，靠手动记录，最终死于没人录入 |

**共性缺陷：都要求用户主动录入，而没人愿意录入。**

### 我们的差异点

**① 语音是唯一的零摩擦录入方式**
这是**唯一一个把「记录关系」的成本降到 3 秒**的方案。
竞品不是没想到做关系管理，而是**没能解决录入摩擦**这个致命问题。

**② 移动 + 原生，而不是网页**
麦克风、后台通知、系统集成 —— 这些恰恰是「主动提醒」原则的前提。
做网页版会直接失去产品的一半价值。

**③ 只做关怀，不做销售**
聚焦带来两个好处：面向个人而非团队（隐私压力小、决策链短）、
概念简单（不需要培训就能理解）。

**④ 从「记录工具」升级为「行动建议」**
大部分工具止步于「帮你记」；我们回答的是「**今天该联系谁**」。

### 但我要诚实说明：我们的护城河不深

语音识别是公开能力，关系状态判定是可复制的规则，
邮件草稿生成是同质化的。**真正的壁垒只可能来自两点：**

1. **交互打磨的细致程度** —— 语音在真实场景（嘈杂、口音、说错话）下的鲁棒性
2. **关系判定模型的准确度** —— 阈值定得好不好，直接决定提醒是「贴心」还是「烦人」

这两点都是慢功夫，不是功能清单能体现的。**这是本产品最大的风险。**

## 8. 主要产品风险（诚实评估）

作为产品文档，这一节比上面的功能列表更重要。

**风险 1：语音的鲁棒性决定生死**
在安静环境下说「周末给妈妈打电话」识别没问题；
但在嘈杂环境、有口音、或说了一句复杂长句时，识别错误会让用户彻底失去信任。
**一次严重的误识别（比如建错日程、挂错联系人）比十次成功更影响留存。**
我们已做的防护：联系人重名时主动询问、识别失败时明确提示而非静默失败、
支持取消与改期。但这仍是最大的技术风险。

**风险 2：「117 天未沟通」这个阈值可能不成立**
不同关系类型的合理联系频率差异极大 ——
直属下属可能两周，跨部门同事可能半年。
用统一阈值会既漏报又误报。**误报（提醒了不该提醒的人）会快速消耗用户耐心。**
这需要真实用户数据来校准，我们目前只有假设。

**风险 3：冷启动摩擦力很大**
用户第一次打开看到空名册，很可能直接退出。
导入通讯录涉及隐私授权，手动录入又太累。
**「让新用户在前 60 秒内感受到价值」这件事我们还没解决好。**

**风险 4：隐私敏感度**
「关系状态」「多久没联系」是相当敏感的私人数据。
用户会担心：这些数据存在哪？谁能看到？会不会被用来评估我的绩效？
我们目前的答案（个人账户隔离、数据只在用户自己账号下）是必要的，但**可能不够**。

**风险 5：提醒容易变成打扰**
「主动提醒」和「骚扰」只有一线之隔。
如果提醒太频繁、太不准确，用户会关掉通知 —— **而通知一旦被关，产品就死了。**
这也是为什么我们把「不在新手引导时申请通知权限」作为一条硬性原则：
把权限请求放在用户真正需要它的时刻（保存带提醒的日程之后）。

## 9. 验证思路

产品判断需要用行为验证，而不是靠功能数量。我们关注的信号：

| 假设 | 验证方式 |
|---|---|
| 语音真的比打字省事 | 对比同一个日程的语音 vs 手动创建耗时 |
| 「需要关注」清单有人真的会用 | 洞察页的查看率、从洞察页产生日程的转化率 |
| 提醒会被行动，而不是被关掉 | 通知点击率、通知权限的关闭率 |
| 阈值判定是否合理 | 用户对「高优先级」标记的接受度（是否忽略） |

**最关键的指标是「从洞察页产生关怀日程的比例」** ——
如果用户看了「需要关注的人」却从不采取行动，那这个产品就只是个好玩的语音 Demo。

## 10. 一句话总结

> **私人关系的衰减是静默的，而人们不是不在乎，是记不住、也懒得记。
> TalentMate 伴贤用语音把记录成本降到接近零，主动告诉你今天该关心谁，
> 并在日程开始前提醒你 —— 让「维护关系」这件事第一次变得可持续。**

**边界：** 我们只帮你记得和安排，那句问候仍然要你自己说。
